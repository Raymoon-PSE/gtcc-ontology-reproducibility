GTCC PROVIDER-INTEGRATION STUDY — PRE-IMPLEMENTATION PROTOCOL
14 October 2026

1. Question and decision
Does an RDF/RDFS implementation differ from a capable indexed-JSON implementation in the observable changes needed to integrate independently authored provider descriptions into a fixed GTCC workflow? Test correct integration first, then characterize where changes occur. An ontology advantage is a hypothesis, not the desired acceptance result. Continued parity is an informative outcome and ends this planned experiment; it is not permission to keep adding favorable tasks.

2. What is new
Earlier studies used common authored facts or simple stream adapters. This study introduces separately authored provider vocabularies, explicit cross-provider mappings, transitive equipment classes, versioned interfaces and qualified identifiers. The providers remain synthetic artifacts authored together by one agent context independent of the future arm implementers. A and B were not authored by two independent organizations or contexts. They are not independent industrial organizations, external datasets or independently maintained applications. The study can examine integration behavior and change locality. It cannot establish industrial interoperability, maintenance savings or superiority of ontology in general.

3. Process coverage and physical evidence
Use all seven solved boundaries: GT exhaust, HP steam, hot reheat, LP steam, ST exhaust, cold reheat and condensate. The frozen 5 and 25 degC complete-cycle outputs come from the already verified later linked-cycle source, not the original manuscript v0.3.0. Both return streams belong to that solved loop. See fixtures/provenance.json and the accompanying prior archive for hashes and reproduction.
This experiment governs provider data ingestion, normalization and queries over solved outputs. It does not modify the solver, discover a flowsheet, rerun existing diagnosis through a new interface or improve physical predictions. A full set of process boundaries is not proof of full application integration. No original EKLM file is changed.

4. Arms and fairness
RDF: explicit equipment vocabulary and mapping facts held in RDF; RDFS-style transitive class traversal and native query facilities allowed. Eligibility ancestry and identity/mapping resolution must actually read the RDF graph, not a parallel JSON registry; audit this before interpreting the arm comparison.
JSON: indexed maps/lists carrying the same primitive facts, qualified identities, subclass links, mappings and versions; arbitrary traversal, indexes, joins, caches and reusable validation allowed. Do not cripple JSON to direct-key lookup or deny it semantic relationships.
Both arms receive identical engineering information, released requirements, numeric fixtures, query contract and conversion examples. RDF conversion/import code counts as arm code. JSON preprocessing and index construction count as arm code. Neither may embed expected test outcomes, depend on the other arm, or inspect acceptance fixtures before original scoring. No shared arm validator or converter: the implementations independently realize the same specification. Third-party dependencies must be recorded; standard libraries are permitted. Native facts must be semantically equivalent; initial conversion is audited before interpreting representation effects.

5. Stages and replication
Two implementation replicates per representation, four fresh implementer contexts in total. Each uses the same available model/configuration where possible; record exact reported settings and unavailable settings. These are agent replicates, not independent human developer samples. Do not estimate population effects or human time savings.
Stage 0: implement provider-v1 integration and three fixed queries; freeze initial implementation and evaluate before releasing Stage 1.
Stage 1: release the v2 provider changes. Permit configuration and code edits. Freeze first attempt, run the original acceptance suite plus stage checks, record results and repairs.
Stage 2: release the v3 provider changes and scoped conflict cases. Repeat the same checkpoint and evaluation procedure. Prior tests remain regressions and are not counted as new independent tasks.
No other change stages will be added after outcomes are inspected. A new research question requires a separately dated protocol, not amendment of these results.

6. Output contract
Each accepted scenario returns exactly seven canonical boundary records with finite T (degC), P (MPa), m_dot (kg/h), and w (mass fractions), plus provider namespace, source schema version, original qualified port ID, and resolved class ancestry. Retain canonical boundary identity even when a provider renames fields or ports. Include explicit provenance linking each converted quantity to the provider field and declared unit. Order of input documents, declarations and mappings must not change the result.
Each query uses only this public contract:
Q1: retrieve all seven boundaries, with canonical units and provenance.
Q2: select boundaries by canonical ancestor class through a transitive subclass chain; no predeclared leaf list.
Q3: retrieve both steam-water return boundaries with qualified source identities and the requested schema revision.
The three queries are test consumers, not existing production dashboard/report/diagnostic applications. Their initial sources and every subsequent edit are checkpointed.
Errors reject the whole integration request without a partial accepted result. Error classes: INVALID_SCHEMA, UNRESOLVED_CLASS, AMBIGUOUS_MAPPING, MISSING_BOUNDARY, DUPLICATE_BOUNDARY, INCOMPATIBLE_UNIT, INVALID_VALUE, VERSION_MISMATCH. When multiple errors apply, any applicable documented class is acceptable; prefer isolated single-error cases. Source inputs must not be mutated.

7. Mapping and physical-value rules
Port identifiers are triples (provider ID, port namespace, local port identifier). Type identifiers are pairs (provider ID, local type identifier). Equal local labels in different namespaces are distinct. Explicit mappings, not lexical similarity, determine equivalence to canonical classes and boundaries. Two contradictory targets for the same qualified identifier are rejected. Identical assertions are logically idempotent; textual repetition is not an error. Class parent references must resolve; cycles are invalid for this declared acyclic equipment taxonomy. The supplied wire format permits one parent_type_id (or null for a root). Multiple inheritance is outside this protocol. A node with no path to the required mapped ancestor is incompatible.
All units are explicitly declared. Allowed temperature units: degC and K. Pressure: Pa, bar and MPa. Mass flow: kg/s and kg/h. Use K = degC + 273.15, 1 MPa = 10 bar = 1000000 Pa, 1 kg/s = 3600 kg/h. Temperature must be above absolute zero; pressure strictly positive; mass flow nonnegative; compositions finite and nonnegative, nonempty, sum to one within absolute 1e-8. JSON booleans are not numbers. Reject non-finite values rather than coercing them. Preserve supplied compositions without inferred chemistry. Other units are rejected.
Comparison tolerance: rtol 1e-10 and atol 1e-6 for scalar physical quantities; composition atol 1e-8; exact equality for identities, versions, case decisions and provenance field/unit strings. Do not relax tolerances after observing an arm. Existing physical convergence and conservation values are source provenance, not new acceptance measurements.

8. Frozen acceptance design
protocol/CASE_PLAN.json defines requirement-level acceptance families before arm implementation. Each valid family runs over both frozen ambient scenarios and compares to the canonical physical fixture, not merely arm-to-arm equality. Independently hand-computed unit examples exercise affine temperature and scaled pressure/mass conversions. Negative variants have one stated mutation and expected rejection. Future executable acceptance code must implement this plan and be frozen/hash-verified before any implementer is started; this protocol freeze alone is NOT a claim that executable tests already exist.
Stage 0 baseline checks must pass before interpreting change locality. Each stage receives an immutable first-attempt checkpoint and at most two repair attempts. Preserve all failures, messages, outputs and repaired checkpoints. If requirements or evaluator are defective, retain original scores, label the defect and apply the same correction to every arm; record amended-suite scores separately. Post hoc discoveries are separate outcomes.

9. Metrics and interpretation
Primary: per-case correctness against the frozen oracle, including negative cases; original first attempt and final attempt separately. Report results per replicate, stage and family. Never treat repeated scenarios/assertions as independent engineering tasks.
Secondary: changed source/configuration files, AST-level changed functions when practicable, added/removed lines, mapping assertions edited, consumer-query edits, explicit validation rules edited, required manual leaf-type enumeration, and regression/repair counts. Separate provider-supplied changes from integrator-authored changes and automatic native serialization. Record complete diffs and dependency versions. Logical fact counts are not developer effort. No composite weighted score or post hoc weighting.
Wall-clock agent/tool time is descriptive only. No human-work benefit claim without observed human work. No timing comparison is planned here; previous metadata microbenchmark remains separate.
A configuration-only change in both arms is parity. A difference in edit locality is an observed implementation difference until shown not to result from initial architecture, coding style or unequal information. Report all four replicates and mixed results. Shared vocabulary expressiveness alone is not an observed integration benefit.

10. Stop and publication decision
Execute the fixed two changes, complete the bounded repair budget, and independently review failures and diffs. If a consistent, requirement-relevant difference appears across both replicates, describe that specific result and its plausible implementation confounds; it is not automatic proof of ontology causality. If parity persists, retain the architectural case-study framing and do not claim maintenance superiority. If an arm fails baseline, report incomplete comparison rather than claiming the other representation is better. After this study, decide journal fit rather than repeatedly enlarging the software until a favorable result appears.

11. Isolation and status
Stage-release separation and acceptance withholding are procedural instructions, not a secure filesystem boundary. Authoring context sees provider requests; fresh implementers must not inherit it. No public preregistration or external timestamp authority is claimed. A local manifest freezes bytes and date before implementation. No arms have been implemented or scored in this protocol package. No manuscript result, repository release or journal submission is created by preparing it.
